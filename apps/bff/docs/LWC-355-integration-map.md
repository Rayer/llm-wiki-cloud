# LWC-355 Query integration map

**Status:** bounded integration map plus strict cache prerequisite. LWC-354's bounded Query reader ABI is available, while active dictionary and source-snapshot lookup/publication seams remain open. This map does not edit `internal/profiletags`; cache changes are limited to an optional pinned-corpus read API, with no provider calls or cloud reads.

## Active tuple, generation pin, and source snapshot seam

Resolve `ProfileState.active` once per request through the existing Profile repository. If there is no Profile or no active tuple, use the existing Query behavior with no Tag filtering or bundle read. A Profile read error is not an absent Profile: return a visible integration failure rather than silently using latest. For an active tuple, read all revisions from that one snapshot (`content_generation`, dictionary, Tag set, Query rules, candidate) and validate their cross-references before matching. Artifact absence, malformed bytes, a wrong revision/digest/generation, incomplete coverage, or a missing canonical corpus must fail the Query visibly; never read staging, borrow `current.json`, or downgrade to the baseline path.

`internal/gcs/client.go` currently pins only `current.json`. Published content objects live under `.lwc/publish/generations/{id}/...`; the publisher now also retains each exact manifest at `.lwc/publish/generations/{id}/manifest.json` before current-manifest CAS. Add a by-ID pin/read seam in `internal/gcs/client.go` plus its optional storage capability and `internal/gcs/generation_view_test.go`; it must load that immutable manifest for the requested ID, validate exact `generation_id`, and read files by object generations and digests in the manifest. A missing archive or file is an error, never a latest fallback. Keep the old view token partitioning: the G1 and G2 cache entries must have distinct view tokens.

`cmd/olw_worker/main.go` materializes exact `sourceSnapshot.RawBytes`/`RawSHA256`. `cloud_publish.go` writes a private post-run `cache/source_status.json` receipt for those captured bytes, validates `sourcestatus.Receipt.LastIngestedRawSHA256`, writes create-only `.lwc/profile/tags/source-bytes/v1/{content_digest}.txt` objects and a versioned source-snapshot inventory, then stores its exact byte digest in `generation.Manifest.source_snapshot_digest`. The inventory records stable source IDs, validated raw paths, exact raw-byte digests and immutable byte-object generations; compile generations retain unchanged rows only when current ID-map membership and receipts match, while the output-only suggested-query stage carries forward the previous inventory only if all content inputs and source identities are unchanged. This uses `cache/source_status.json` because it contains `LastIngestedRawSHA256`; `cache/raw_status.json` is the separate OLW state-db status artifact. Source bytes, inventory and archived generation manifest are verified before current CAS; a losing CAS may leave immutable orphans but is not reported as a committed generation. The generation manifest digest remains outside the source inventory to avoid mutable self-reference.

Older manifests can omit `source_snapshot_digest` for legacy/baseline compatibility, but a Profile read that needs source inventory must fail visibly if it is absent; do not fabricate an empty inventory. Retain archived manifests, generation files, source snapshots and Profile artifacts while any active/candidate/job/query lease references them; deletion and digest mismatch must fail closed.

The 354 Query ABI is now available: `ReadBundle(ctx, Store, ActiveRef, InventoryIndex, Dictionary) (Bundle, error)` reads exactly the immutable Tag set and Query rules; `InventoryIndex` contains generation/concept/id-map/source-snapshot digests and `ItemRef`s; `Bundle` exposes the set, rules, `RequirementStatus(requestedTagIDs, kind)`, and `RequireSupported(requestedTagIDs, kind)`. The reader validates complete exact row coverage without re-reading bodies or individual decision objects. Its storage interface is bounded read/create, so the request adapter needs a small read-only bridge over the pinned Project store.

Proposed runtime injection: in `internal/handler/v1/endpoints.go`, read Profile state once before choosing the corpus view; if active, pin that generation, obtain the exact active dictionary ref, build the inventory index, and read the bundle. Pass the result as an optional internal `profiletags.Bundle` on the existing `query.Request`; this leaves the `query.Executor` method and both current production executor compositions intact. The inventory/body loader must share one canonical `cache/concepts.jsonl` read. Read `cache/id_map.json` once and the generation-addressed source-snapshot inventory once; derive source item refs from its rows without reading source bytes. Reuse a stable cache token for repeat reads of one pinned view; G1 and G2 must have distinct tokens and cache entries. With no active tuple, omit the optional bundle and keep the existing baseline.

The cache prerequisite is implemented as `func (*Cache) PinnedCanonicalSnapshot(ctx context.Context, reader Reader) (PinnedCanonicalSnapshot, error)`. It returns `PinnedCanonicalSnapshot{Identity storage.QueryGenerationIdentity, Entries []CanonicalEntry}`; each `CanonicalEntry` contains `Entry`, canonical frontmatter `StableID`, and `ContentDigest` (lowercase SHA-256 of that exact JSONL row without its line ending). `planConceptCacheIDs` in `cmd/olw_worker/concept_reconcile.go` serializes each canonical row with compact `json.Marshal` output followed by LF; `profiletags.inputFor` hashes the validated row bytes directly as `Content`, then hashes its compact evaluator envelope. The API preserves those row bytes for the row digest, checks `Identity.ConceptsDigest` in the manifest's `sha256:<hex>` form against the complete JSONL bytes, and returns visible read, digest, parse, or stable-ID errors without `ListConcepts`/`GetPage` fallback. A valid empty JSONL is a strict empty snapshot, while missing or corrupt JSONL fails; `All` retains its existing fallback behavior, including after an empty strict snapshot. A prior JSONL load under the same pinned view can supply cached raw bytes, so the snapshot API does not need a second artifact read.

In `internal/queryquality`, join `Bundle.Set.Rows` to candidate `cache.Entry` by canonical frontmatter ID and `kind=concept`, then preserve the current body matcher and selector. Derive recognized requested Tag IDs only from an explicit current Query constraint, call `RequirementStatus(requestedIDs, Concept)`, and expose unsupported IDs in a separate structured Query result status. Do not call `RequireSupported` as a whole-dictionary rejection and do not turn `required_candidate` into a gate for every query. An unknown query token stays out of `requestedIDs` and remains an ordinary body-search term. The currently validated writer rules set all hard gates false and label a required proposal `unsupported_required`; therefore no hard filtering ships under this ABI. Enabling a future hard gate requires a reviewed quality policy and a separately updated reader contract. The precise mapping from the current Query plan's required criterion to explicit Tag IDs remains the only Query policy question; the package ABI reports support for given IDs but does not infer user intent.

## Query policy and truthful fallback

- `query_use=preferred` adds a deterministic bounded ranking bonus only after existing body/query matching; it cannot create a result that failed normal lexical eligibility or bypass `ResultSelector`.
- `required_candidate` in the dictionary is an intent proposal, never sufficient by itself to filter. A hard gate is allowed only when the active Query rule explicitly enables it under a separately versioned, reviewed quality policy. The current 334 synthetic holdout does not meet that gate. For an explicitly requested condition with no approved gate, return a distinct structured “required condition unsupported” status; do not silently report that the condition was enforced. An unrelated query remains on normal matching even when the dictionary contains other `required_candidate` tags.
- When an enabled hard condition is explicitly relevant to the query, only an exact `concept` row for the canonical stable ID and Tag ID with judgment `match` satisfies it. `unknown` and `not_applicable` are completed judgments but do not match; they do not become errors or `no_match` in storage. A missing/extra/duplicate row or generation/content digest mismatch is bundle corruption and fails the request.
- An unrecognized query token remains an ordinary search token: preserve body-search fallback and attach no Tag gate to it. This is separate from a stored `unknown` judgment, which cannot satisfy an enabled requirement.
- Model-only geographic direction or containment remains a ranking hint at most. The LWC-349 ambiguous cases disallow it as a required hard gate.
- Hard-gate relevance must be request-scoped. The current Query plan already distinguishes required/preferred criteria, but the exact mapping from an explicit Query criterion to a Profile Tag has not been frozen. Do not interpret every active required-candidate rule as applying to every query.

## ABI status and unresolved decision

The coordinator relayed the corrected 354 ABI and confirmed its Query reader is now scoped by requested Tag IDs and `kind`; writer-side deep readback remains separate. `profiletags.ReadBundle` consumes `ActiveRef{ContentGeneration, DictionaryRevision, TagSetRevision, QueryRuleRevision}`, a caller-built `InventoryIndex{ContentGeneration, ConceptsDigest, IDMapDigest, SourceSnapshotDigest, Items []ItemRef}`, and a validated `Dictionary`. It loads only set/rules and rejects incomplete coverage or cross-generation rows. `RequirementStatus` returns requested IDs that are unsupported; `RequireSupported` wraps that as an error. Use the former to report unsupported intent while preserving eligible results; reserve the latter for an explicit product decision to reject that request. Build the active ref only after checking the historical candidate named by `ProfileActive.CandidateID` agrees on generation and dictionary revision.

Three binding inputs still need owner agreement: (1) a read of the historical active candidate's exact dictionary ref, even when `ProfileState.Candidate.CandidateID != ProfileState.Active.CandidateID`; (2) validation of that immutable dictionary that does not use newer current requirements; (3) the generation-addressed source-snapshot manifest digest needed to construct `InventoryIndex` before `ReadBundle` loads the Tag set that also contains that digest. The corrected ABI is usable once those lookup seams exist; the parent explicitly confirmed that this is not yet full package/publication integration.

The remaining decision is `explicit Query criterion -> requested Tag IDs -> unsupported status`. Current `QueryPlan` has required/preferred criteria but no declared Profile Tag ID field, and the package ABI does not classify free text. Next check: agree a deterministic request-scoped mapping (or a wire-level explicit Tag request) and add a fixture where a known Tag is requested plus one where an unrelated query has the same active dictionary. Stop condition: no hard gate until this mapping and the reviewed quality policy are explicit.
