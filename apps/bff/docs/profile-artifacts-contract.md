# Profile V1 derived artifacts — proposed LWC-352 contract

**Status:** Choice A is approved for initial Project bootstrap: compile guidance is derived, previewed, explicitly confirmed, and applied to the first compile before content generation. Existing-generation dictionary and guidance envelopes follow the immutable contract below. The existing [LWC-351 contract](LWC-351-profile-contract.md) and [LWC-209 report](LWC-209-implementation-report.md) own API/state behavior; LWC-354 owns Tag decisions and coverage, LWC-355 owns query rule and reader integration, LWC-353 owns the Synto adapter and compile callback. Profile belongs to Project and uses Project read/edit authorization. No separate Profile owner policy or LWC-283 migration is introduced.

## Inputs and timing

- The source of user intent is the **entire current ordered** `ProfileState.requirements` array of `{id,text}`. Preserve each ID, order, and text verbatim, including blank text. A removed ID is absent from every new artifact; neither prior dictionary nor prior guidance supplies missing requirements. Derivation never edits the saved input.
- `input_digest` is exactly 209's `profileRequirementsDigest`: lowercase SHA-256 hex of Go `encoding/json.Marshal([]ProfileRequirement)` on that ordered array. Both new `ProfileDerivedRef.input_digest` values equal the current requirements digest. For `[]`, it is `4f53cda18c2baa0c0354bb5f9a3ecbe5ed12ab4d8e11ba873c2f11161202b945`.
- Manual derivation starts only after the persisted three-minute debounce and pins one confirmed content generation. For nonempty requirements and an active Profile being cleared to `[]`, read its manifest-listed `cache/concepts.jsonl` once and `cache/id_map.json` once. `canonical_concepts_digest` is SHA-256 of those exact JSONL bytes; absent/unlisted/invalid JSONL is an error, while a valid empty file has the empty-byte SHA-256. Validate rows and stable concept IDs against that generation's `cache/id_map.json` and canonical active concepts; do not infer identity from slug or include dormant concepts. Use the generation snapshot, never a moving `current.json` read midway. This file is context for deriving definitions and guidance, not a list of inherited Tag decisions. A cleared active Profile emits neutral artifacts without calling a provider, but binds their digest to the actual pinned concepts bytes.
- If the generation has **zero active canonical concepts**, derive from the full requirements with an empty concept context; emit valid artifacts and `tags` if justified by requirements. Do not fabricate concept examples, fail solely because the set is empty, or silently reuse previous concepts. An initially empty/no-active Profile remains no-work under 209. Clearing an active Profile to `[]` follows 209's normal delayed manual candidate/confirmation path and emits neutral artifacts below.
- A fully successful compile with confirmed manifest/receipt may derive a new **dictionary only** from the current full requirements and new canonical concept snapshot, even if words appear unchanged. Partial compile changes no dictionary; an ambiguous manifest commit requires readback before scheduling. Compile reconciliation waits while a manual derivation, confirmation, or activation is pending, including failed manual derivation. A stale requirements revision/digest causes a new reconcile from current state; it must not publish an old candidate. No automatic full-library recompile.

### Initial Project bootstrap: nonempty requirements, no generation

After the three-minute debounce, derive only compile-relevant guidance from the full current ordered requirements without concept context. Persist a generation-free preview and immutable guidance object, require explicit confirmation, and let the first compile pin that exact confirmed reference. The successful publisher result must carry the worker's typed bootstrap reference captured at compile start together with its committed manifest object generation and canonical concepts digest in the in-process `ProfileCompileSuccess` input; merely observing a current confirmed pointer is not evidence that the batch consumed it. Promotion rechecks the pinned generation evidence and, in the Firestore transaction, requires the consumed reference to still match the confirmed bootstrap reference for the same Profile revision and ordered input digest. The first compile must report pending confirmation when requirements are nonempty and no current confirmed bootstrap reference exists; it must not silently use base guidance or use an unconfirmed preview. No dictionary candidate, Tag job, active tuple, fake generation, manifest, concept digest, or synthetic corpus identity is created by this bootstrap. A later successful generation enters the ordinary dictionary/tag coverage activation path.

Bootstrap artifact bytes use compact canonical JSON with these ordered fields and types:

```json
{"schema_version":"profile.bootstrap-guidance.v1","profile_revision":1,"input_digest":"<64 lowercase hex>","model_version":"<provider model ID>","prompt_version":"<prompt ID>","compile_guidance":"<compile-relevant instructions>"}
```

The artifact revision is SHA-256 of these exact bytes and is not embedded in the object. The relative path is `.lwc/profile/bootstrap-guidance/v1/{revision}.json`. The Project Profile state pointer binds `revision`, `profile_revision`, and `input_digest`, and stores `status=preview_ready|confirmed`, `confirmed_at`, and a preview with `guidance_diff` plus one accounting row per current requirement: `{id,disposition,explanation}`. Disposition is `compile_guidance|dictionary_or_query|both|limitation`; every requirement must have an explicit row, including an explicit limitation if it could not be represented. Confirmation requires the exact artifact revision, current expected Profile revision, and current ordered requirements digest in one Firestore transaction. A new save clears the current bootstrap pointer and supersedes the old attempt, so late output and stale confirmation cannot apply. The artifact remains immutable historical data.

The bootstrap reader enforces the same 1 MiB strict UTF-8 JSON, duplicate-key, unknown-field, trailing-data, hash, and reference checks as generation-bound artifacts. Its envelope intentionally has no generation or concept field. Compile start pins the confirmed ref once and carries the exact `compile_guidance` content through execution; subsequent compile-auto dictionary candidates preserve the currently active guidance reference unchanged.

## Immutable objects and identity

Objects live in the existing GCS Project scope `users/{userID}/projects/{projectID}/`, under these relative paths:

```text
.lwc/profile/derived/dictionary/v1/{revision}.json
.lwc/profile/derived/guidance/v1/{revision}.json
```

`{revision}` is 64 lowercase SHA-256 hex characters of the **exact persisted UTF-8 JSON bytes**, excluding any newline. The JSON envelope does not contain its own revision. The writer emits compact JSON in the field order shown below with Go `encoding/json` string escaping, no maps or insignificant whitespace; arrays keep their specified order. Sort `tags` by `id` and each tag's `requirement_ids` by current requirement order. This makes retries of identical output byte-identical; different model outputs get distinct revisions. The GCS write uses create-only (`DoesNotExist`/generation precondition zero); an existing path is accepted only after byte equality. Never overwrite, delete for replacement, or use a mutable `latest` alias. The path is an object key **inside** the existing Project scope, not a new bucket or trust boundary. No Firestore schema migration is required.

The `ProfileDerivedRef` stored by 209 is `{revision,input_digest,model_version,prompt_version,schema_version}` copied from the validated envelope and byte hash. For dictionary, `schema_version="profile.dictionary.v1"`; for guidance, `schema_version="profile.guidance.v1"`. `model_version` is the provider-returned model ID when a model ran; `prompt_version` identifies the exact prompt/template. Neutral deterministic output uses `neutral-v1` for both. The **dictionary revision includes** `content_generation` and `canonical_concepts_digest` because both are envelope bytes. The guidance envelope records its derivation generation as provenance, but the guidance artifact remains reusable by later compile generations.

Dictionary envelope, with exact top-level key order and types:

```json
{"schema_version":"profile.dictionary.v1","input_digest":"<64 lowercase hex>","content_generation":"<confirmed generation ID>","canonical_concepts_digest":"<64 lowercase hex>","model_version":"<returned model ID or neutral-v1>","prompt_version":"<prompt ID or neutral-v1>","tags":[{"id":"<stable token>","definition":"<what the tag means>","applies_to":["source","concept"],"match_rule":"<positive evidence>","non_match_rule":"<negative evidence>","unknown_rule":"<insufficient or ambiguous evidence>","requirement_ids":["<current ID>"],"query_use":"preferred"}]}
```

The tag `id` is unique within the dictionary and is an ASCII token matching `[a-z][a-z0-9_]{0,63}`. `definition`, `match_rule`, `non_match_rule`, and `unknown_rule` are nonempty strings. `applies_to` is a nonempty subset in fixed `source`, then `concept` order. `requirement_ids` is a nonempty subset of current requirement IDs. `query_use` is `preferred` or `required_candidate`: it records the proposed user intent, **not** evidence that a hard filter is safe to enable. Every retained requirement must be represented in the preview as Tag/query intent, compile guidance, both, or an explicit derivation limitation; no requirement may silently disappear. A source and a concept receive separate decisions under the same definition, with their own `kind`, stable ID, content digest, and dictionary revision. A concept never inherits the decision of a cited source. Unknown and not-applicable are completed judgments but do not match a necessary condition; provider errors are missing work, not `no_match`.

Guidance envelope, with exact top-level key order and types:

```json
{"schema_version":"profile.guidance.v1","input_digest":"<64 lowercase hex>","source_content_generation":"<confirmed generation ID>","canonical_concepts_digest":"<64 lowercase hex>","model_version":"<returned model ID or neutral-v1>","prompt_version":"<prompt ID or neutral-v1>","compile_guidance":"<plain UTF-8 instructions for Synto adapter>"}
```

`compile_guidance` is a standalone instruction string, not a patch to prior guidance. Derivation considers **all** current requirements, but this field contains only intent applicable to writing or structuring material during a future compile; Tag detection, query filters, ranking, and provider decision rules stay in the dictionary/preview, never get copied indiscriminately into Synto's writing prompt. A Tag/query-only Profile can have `compile_guidance=""` with nonempty requirements and nonempty tags. The preview accounts for each requirement and explains whether it affects Tags/query, compile guidance, both, or could not be represented; removed requirements appear in neither artifact. The BFF writer and Synto worker reader need only this envelope and the ref; neither imports BFF handler types. LWC-353 pins the active `guidance_revision` at compile start, validates the object, and materializes the exact guidance as the pinned Synto wheel's `vault-schema.md` only after verifying that wheel actually consumes it. The adapter's observed 1500-character budget is checked on the final materialized text: reject visibly if exceeded, never truncate. This budget is **not** a Profile field limit.

Readers resolve refs only after Project authorization/service claim validation, derive the relative path from kind and revision, then check path segment shape, byte SHA-256, strict envelope schema (including rejection of unknown or duplicate keys), matching `schema_version`/`model_version`/`prompt_version`/`input_digest`, and the dictionary's expected content generation/concept digest. Guidance's source generation is provenance, **not** required to equal a later compile generation. Read at most **1,048,576 bytes per artifact** and reject any larger object, along with missing, malformed, or mismatched objects; do not fall back to an older or latest artifact. GCS object bytes are immutable once referenced; candidate/active pointers remain Firestore's only mutable publication control. For compile-auto, copy the **exact active guidance ref** into the new candidate and write no new guidance object; the new dictionary ref has the current requirements digest and confirmed new generation. `preview.guidance_diff=""`.

## Neutral and no-concept fixtures

The neutral `[]` dictionary has `tags=[]`; the neutral guidance has `compile_guidance=""`. Both use the current confirmed generation, the SHA-256 of that generation's exact pinned concept JSONL bytes, and deterministic `neutral-v1` provenance. The neutral guidance means the adapter supplies no Profile-specific instruction; it must not erase base Synto configuration. LWC-354 still validates the new generation's coverage/no-op tag set before 209 can switch the active tuple; a candidate is not automatically active merely because its dictionary is empty.

## Consumer handoff and evidence limits

- **352 writer:** `internal/profileartifacts` implements strict, content-addressed artifact validation and create-only writes. `internal/profilederive` implements full-requirements bootstrap/manual/compile-auto derivation, ordered preview accounting, canonical concept snapshot validation, and callable attempt/reconcile executors. `Handler.RunProfileDerivation` authorizes the Project, claims a due attempt transactionally, pins the current manifest once when needed, reads only listed ID map/concepts, persists immutable output, and commits through 209's revision/attempt/digest-fenced transitions. `Handler.RunProfileCompileDerivation` creates dictionary-only candidates for active Profiles and promotes confirmed bootstrap guidance into a normal generation-bound artifact on the first successful generation. The first-generation promotion transaction and callable bootstrap path are covered by Firestore emulator tests with explicitly labeled deterministic fake providers. A delayed dispatcher/service-claim endpoint and production binding from the BFF's configured LLM client are not wired; these callables are not themselves a due-job runner.
- **353 compiler:** resolve the active guidance object at compile start, verify ref and budget, and demonstrate real `vault-schema.md` consumption by the pinned Synto 0.7.0 adapter. Recompile all remains rejected before BYOK. Successful generation callback must name the confirmed `generation_id`; partial and outcome-unknown paths do not derive new rules.
- **354 tagger:** consume dictionary by exact ref; pin confirmed generation and enumerate source/concept keys from its canonical manifest/id map, not small-file rescans. Tag metadata/coverage schema is 354's separate contract; it must include `(kind,stable_id,content_digest,dictionary_revision,tag_id)` and final `match|no_match|unknown|not_applicable` or a missing error. `tags=[]` yields an explicit complete empty tag set, not invented matches. Only complete coverage may provide `tag_set_revision`/`query_rule_revision` to 209's `ProfileJobTransition`.
- **355 reader/query:** pin one active tuple and its content generation. It must not read the moving latest generation when active still points to an older one. Exact external Tag metadata decides matches; body mention grep is not Tag truth. `required_candidate` must remain non-blocking until separately validated for production hard filtering; 334's small synthetic holdout did not establish that gate. 349 found geographic ambiguity false accepts, so unresolved place names stay unknown and model-only geography cannot gate.

### Implemented callable slice and remaining integration

`internal/profileartifacts` owns compact envelope encoding, exact-byte SHA-256 references, strict UTF-8/JSON validation, the 1 MiB cap, and create-only write plus exact readback. `internal/profilederive` owns full ordered requirements input, compile-relevant bootstrap guidance, complete preview accounting, strict output validation, provider-returned model provenance, canonical concept rows, and manual/neutral/compile-auto derivation. `Handler.RunProfileDerivation` adapts the manual/neutral and generation-free bootstrap paths to the persisted 209 attempt state. A Firestore emulator test exercises this real handler entrypoint and transactional bootstrap completion with a deliberately synthetic provider response and in-memory create-only object store. No live provider request was made.

`internal/llm.ChatWithMetadata` returns provider-reported model metadata while the existing `Chat` method preserves its old behavior; focused transport tests verify one request and one call receipt. Production Profile derivation is not yet bound to the configured BFF LLM client. The current BFF handler construction passes a nil LLM client, and no dedicated Profile worker URL/service-claim contract is present. The durable debounce persists an attempt and the callable executor validates/claims it, but no delayed dispatcher currently invokes that executor. Do not treat `pipeline/run` as a substitute. A shared authenticated Cloud Run scheduling seam and provider binding must be supplied and tested before claiming the delayed worker is runnable.

The first-generation state path is now explicit: after the successful compile callback, `RunProfileCompileDerivation` copies the exact confirmed bootstrap writing instruction into a `profile.guidance.v1` object tied to the pinned generation, derives the new dictionary, and transactionally stages a compile-auto candidate with no active pointer. Tag coverage can then activate that candidate through the normal 354 transition. Later compile-auto candidates keep the active guidance ref unchanged. The callback still needs the shared delayed dispatch/service-claim wiring to invoke it in production.

Actual integration seams: `apps/bff/internal/handler/v1/profile.go` owns `ProfileDerivedRef`, candidate/active and internal worker transitions; `apps/bff/cmd/olw_worker/cloud_publish.go` commits `.lwc/publish/current.json` after source/concept reconciliation; `apps/bff/internal/generation/manifest.go` carries `generation_id` and file digests; `apps/bff/cmd/olw_worker/concept_reconcile.go` rewrites canonical `cache/concepts.jsonl` and ID map; `apps/bff/cmd/olw_worker/synto_execution.py` pins the 0.7.0 adapter; `apps/bff/internal/gcs/client.go` defines the Project object scope. The current GCS `Pin` reads latest; a generation-specific reader or publish gate remains necessary for coherent G1/G2 query reads.

334 ran a bounded 23-call synthetic tagging experiment, and 349 ran a bounded 49-call geography experiment. Their results justify retaining unknown and exact metadata, **not** claiming live writer→reader acceptance or production hard-filter safety. No provider calls, product integration, migration, deployment, or live acceptance are performed by this doc slice.
