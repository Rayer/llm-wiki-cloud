# LWC-354 Profile Tag writer and LWC-355 reader contract

**Status:** coordinator accepted the immutable decision/set/rule shape for a bounded LWC-354 metadata package; `internal/profiletags` implements only that isolated writer/reader/evaluator seam with synthetic tests. The dispatcher, provider adapter, Job entrypoint, IAM, and generation retention below remain integration requirements, not deployed behavior or measured model quality. LWC-209/351 own Profile state and CAS, LWC-352 owns derivation executor, the parent coordinates the shared scheduling seam, LWC-353 owns compile publication and existing worker entry points, LWC-354 owns Tag evaluation/metadata, and LWC-355 owns Query integration.

## Scope, identities, and eligibility

The Tag job consumes the **exact** current candidate dictionary ref from [the derived artifact contract](profile-artifacts-contract.md), the confirmed candidate `content_generation`, candidate ID, requirements revision/digest, and job ID. It checks a scoped service claim through the existing real-Project metadata authority, then transactionally claims the 209 job. A stale save, candidate, job, or generation is `superseded`, never a reason to publish a new active pointer. Initial nonempty requirements without a generation may produce the now-confirmed **generation-free writing guidance for the first compile**; there is no Tag job, fake generation, dictionary candidate, or active tuple until a real confirmed generation exists. An initially empty/no-active Profile is no-work. Clearing an active Profile to `[]` is a normal delayed manual candidate, with an explicit complete empty Tag set after confirmation/coverage checks.

`kind` is exactly `source` or `concept`. Stable source ID comes from the generation's `cache/id_map.json` `source` map; stable active concept ID comes from `cache/concepts.jsonl` frontmatter `id`, cross-checked against the generation's `id_map` active concept/entity mapping. Dormant concepts and redirects are excluded. Enumeration reads the manifest-listed `id_map` and `concepts.jsonl` once and validates their manifest size/digest; it **does not stat or read each concept page**. Duplicate, missing, redirected-only, or conflicting IDs fail the generation coverage build. The complete expected key set is the Cartesian product of every enumerated item and each dictionary tag whose `applies_to` contains that kind. For zero tags or zero items this product is empty and coverage still gets an explicit complete manifest.

For each concept, `content_digest` is lowercase SHA-256 of the exact UTF-8 `cache/concepts.jsonl` row bytes **without its line ending**; a changed row invalidates reuse. For each source, it is lowercase SHA-256 of the exact raw source bytes fed to the evaluator. The evaluator input is compact JSON array `[kind,stable_id,content_digest,content_utf8]`, where `content_utf8` is the exact validated UTF-8 source text or concept row text; `input_digest` hashes that array's exact bytes. There is no hidden changing context. Source bytes must be a retained immutable snapshot tied to the content generation and checked against the generation's `id_map` source identity and the worker's `cache/source_status.json` receipt. `sourcestatus.Receipt.LastIngestedRawSHA256` must equal the pinned source snapshot's raw-byte digest. `cache/raw_status.json` is a separate OLW state-db status artifact and is not the canonical raw-byte receipt. Current mutable raw objects alone cannot prove an old generation's source content. The publisher persists only start-pinned `sourceSnapshot.RawBytes`/`RawSHA256`; it validates the post-run receipt and never rereads mutable raw after compilation. If the receipt and snapshot disagree, source inventory publication fails and the old current manifest remains. No ad hoc source lookup by slug or current raw file is a substitute.

## Immutable wire format

Artifacts reside inside the existing `users/{userID}/projects/{projectID}/` GCS scope. Every `{revision}` is SHA-256 lowercase hex of the **exact compact UTF-8 JSON bytes**, no trailing newline; objects are create-only, and an existing name is accepted only after byte equality. Use strict JSON decoding: reject unknown/duplicate fields, excess size, invalid Unicode, wrong type, and trailing data. Arrays have the sort orders below; serializers use Go `encoding/json` escaping and no maps in hashed envelopes. The reader bounds each object to 64 MiB and verifies the object bytes, revision path, and every embedded digest. A set over the bound fails visibly as `incomplete`; splitting is a later schema revision, not silent truncation.

```text
.lwc/profile/tags/decisions/v1/{decision_revision}.json
.lwc/profile/tags/sets/v1/{tag_set_revision}.json
.lwc/profile/tags/source-snapshots/v1/{source_snapshot_revision}.json
.lwc/profile/tags/source-bytes/v1/{content_digest}.txt
.lwc/profile/query/rules/v1/{query_rule_revision}.json
```

The decision envelope below is one immutable judgment. `rule_digest` is SHA-256 of compact ordered JSON `["profile.tag-rule.v1",tag_id,kind,definition,match_rule,non_match_rule,unknown_rule,configured_model,accepted_returned_models,prompt_version,schema_version]` taken from the **validated dictionary** and pinned evaluator policy. `accepted_returned_models` is a sorted, explicit allowlist. The configured model may be an alias and the provider may truthfully return a versioned ID from that allowlist; neither is fabricated or automatically treated as a failed call. A returned ID outside the allowlist is a missing provider result. This invalidates reuse when the rule or provider identity policy changes, even if dictionary revision changes for unrelated tags. `input_digest` hashes the exact evaluator input envelope, and `content_digest` hashes its source/concept content portion as defined above. The decision lookup key is `(kind,stable_id,content_digest,input_digest,rule_digest)` within one Project scope. A reused decision may belong to an older dictionary revision because the rule digest proves its semantics; the new set row binds it to the current dictionary.

```json
{"schema_version":"profile.tag-decision.v1","kind":"source","stable_id":"s1","content_digest":"<sha256>","input_digest":"<sha256>","rule_digest":"<sha256>","tag_id":"family_friendly","judgment":"unknown","configured_model":"<configured model or deterministic-v1>","returned_model":"<actual accepted provider ID or deterministic-v1>","prompt_version":"<prompt ID or deterministic-v1>","evidence":"<bounded non-sensitive explanation>","confidence":null}
```

`judgment` is exactly `match|no_match|unknown|not_applicable`. `unknown` means evidence is insufficient or ambiguous; `not_applicable` means the tag applies to this kind but the item is structurally outside its domain. Both are completed decisions. `confidence` is `null` unless the evaluator has a calibrated `[0,1]` measure; do not invent numerical certainty. Evidence is bounded to 2 KiB and contains no raw provider response or secrets. Provider timeout, transport failure, malformed output, or exhausted budget produces **no decision object**. Record an operational `transient_failure` or `permanent_failure` beside the job, never a fifth judgment or `no_match`. Deterministic geo parsing may emit `unknown` for unresolved locations. Jev/model-only geographic containment may provide ranking hints but cannot authorize a required hard gate: LWC-349 observed false accepts on ambiguous cases.

The Tag set is a single immutable coverage snapshot. Its `rows` are sorted by `(kind,stable_id,tag_id)` (`source` before `concept`); each row has exact current `dictionary_revision`, `rule_digest`, `content_digest`, `input_digest`, and `decision_revision`, plus the final `judgment`. The writer validates each referenced decision byte hash and key before copying its judgment into the row. `expected_count` equals the enumerated product above, `completed_count` equals `rows.length`, and `missing_count=expected_count-completed_count`. A publishable set requires `missing_count=0`, unique exact keys, no extras, validated source/concept snapshot digests, and matching generation/dictionary. Incomplete staging can be kept as a durable job checkpoint, but has **no** `tag_set_revision` and cannot be referenced by active.

```json
{"schema_version":"profile.tag-set.v1","content_generation":"G2","dictionary_revision":"<sha256>","concepts_digest":"<manifest concepts.jsonl sha256>","id_map_digest":"<manifest id_map.json sha256>","source_snapshot_digest":"<immutable source snapshot manifest sha256>","expected_count":1,"completed_count":1,"missing_count":0,"rows":[{"kind":"source","stable_id":"s1","content_digest":"<sha256>","input_digest":"<sha256>","rule_digest":"<sha256>","tag_id":"family_friendly","dictionary_revision":"<sha256>","decision_revision":"<sha256>","judgment":"unknown"}]}
```

For `tags=[]`, `rows=[]`, all counts are zero, and the generation/dictionary/input inventory digests remain real, validated values. Source snapshot digest is the SHA-256 of the retained snapshot manifest, including an explicit empty manifest if there are zero sources. The set is immutable regardless of whether the manual candidate is later confirmed.

The source snapshot manifest is compact ordered JSON `{"schema_version":"profile.source-snapshot.v1","content_generation":"G2","id_map_digest":"<sha256>","source_status_digest":"<sha256>","rows":[{"stable_id":"s1","raw_path":"<validated receipt path>","content_digest":"<sha256>","object_generation":123}]}`. `source_status_digest` is SHA-256 of the exact `cache/source_status.json` receipt bytes. Sort rows by stable ID; each row points to `.lwc/profile/tags/source-bytes/v1/{content_digest}.txt` at its exact GCS `object_generation`. The publisher writes those immutable byte objects only from start-pinned source snapshots, after writing and validating the post-run `sourcestatus.Receipt.LastIngestedRawSHA256` for those exact inputs. It then reads back by object generation. A duplicate digest path is accepted only after byte equality. A compile G2 retains a G1 row/object only while the current `id_map` still names that source and its current receipt matches the exact prior digest and path; removed IDs disappear, and missing historical bytes fail closed. A non-compile suggested-query generation carries the prior inventory only when all generation files except `cache/suggested_queries.json`, the `id_map`, and the stable source-ID set are unchanged; this preserves the receipt and raw bytes actually used by the preceding compile. It never substitutes mutable current raw bytes for a missing historical object. The manifest object revision is its byte hash and is what `source_snapshot_digest` names. `generation.Manifest.source_snapshot_digest` references this inventory, and the generation manifest is retained create-only at `.lwc/publish/generations/{generation_id}/manifest.json`; source bytes, inventory and archived generation manifest are verified before `current.json` is advanced by CAS. Older manifests may omit `source_snapshot_digest`; when a Profile read requires a source inventory, absence is an error rather than an invented empty snapshot. Legacy maps without the canonical `source` map likewise do not claim source coverage; baseline publication remains supported and a Profile read requiring inventory must fail. Retain the manifest and byte objects as long as any candidate/job/active generation needs them.

The Query rules object is compiled from the same validated dictionary and Tag set. Rules are sorted by `(tag_id,kind)` with source before concept. Each row binds `tag_id`, `kind`, that kind's `rule_digest`, `query_use` (`preferred|required_candidate`), `hard_gate_enabled` (boolean), and `reason_code` (`preference|unsupported_required|approved_required`). The current package always emits `hard_gate_enabled=false` and rejects requested approvals: a reviewed quality policy and geo evidence classifier are not wired. A proposed `required_candidate` therefore emits `unsupported_required`; `Bundle.RequireSupported()` returns a typed error and Query must expose that unsupported/not-satisfied state, rather than treating it as a preference or claiming enforcement. Later enabling any required gate needs an explicit reviewed quality policy, adequate independent holdout, production writer-to-reader evidence, and deterministic geo safeguards. Model-only geographic containment can never independently enable a hard gate. `not_applicable` and `unknown` never count as `match` for a future enabled required condition.

```json
{"schema_version":"profile.query-rules.v1","content_generation":"G2","dictionary_revision":"<sha256>","tag_set_revision":"<sha256>","quality_policy_revision":"none","rules":[{"tag_id":"family_friendly","kind":"source","rule_digest":"<sha256>","query_use":"preferred","hard_gate_enabled":false,"reason_code":"preference"}]}
```

The `query_rule_revision` is the byte hash of this object. For `tags=[]`, `rules=[]`, `quality_policy_revision="none"`; the object still exists. This freezes the LWC-355 handoff: resolve `active` once per Query request; pin **that exact** `content_generation`, `dictionary_revision`, `tag_set_revision`, and `query_rule_revision`; verify all hashes, inventory digests, row keys, rule digests and cross references; then score/filter only items in that generation. Reject a missing/mismatched artifact as an integration error and never mix a current G2 page with G1 active Tag decisions. Do not fall back to latest or read staging. The current GCS `Pin` reads only `current.json`; an old-generation pin/retention API or publish gate is required before this handoff is implementable.

The implemented ABI is `profiletags.ReadBundle(ctx, Store, ActiveRef, InventoryIndex, Dictionary) (Bundle,error)` in `internal/profiletags/query_reader.go`. `InventoryIndex` contains generation, concepts/id-map/source-snapshot digests and `(kind,stable_id,content_digest)` references supplied from an already pinned generation; it contains no source body or per-concept page. The Query path reads exactly two immutable objects, the Tag set and Query rules, and validates hashes, counts, sorted unique keys, inventory references, and set/rule cross references. It does not recreate provider policy from moving environment or fetch individual decision objects. The writer's `ValidatePublication` performs deep decision/source coverage readback before publication. `Bundle.RequireSupported(requestedTagIDs,kind)` is called **only for hard constraints explicitly requested by this Query**; unrelated dictionary rules do not block ordinary searches. The reader currently supports only disabled hard gates, so a requested hard rule returns `ErrUnsupportedRequired` and must be exposed by LWC-355.

## Worker, reuse, retry, and activation

After the three-minute server-time save debounce, the **parent-coordinated shared** durable due-work dispatcher claims derivation intents for 352 and Tag jobs for 354 once a candidate exists. A confirmed compile generation may enqueue compile-auto Tag work immediately if the prior save debounce has expired; otherwise its due time is the saved `scheduled_for`. A new save supersedes older due work. Neither the BFF request nor a Cloud Run Job sleeps for three minutes. A Cloud Scheduler minute tick to a service-authenticated internal dispatch endpoint is the simplest concrete path: it scans indexed due intent/job documents, checks current Project metadata and revision, and calls dedicated Cloud Run Jobs `:run` with scoped project/candidate/job/attempt overrides. The job's Cloud Run service account obtains its own service identity; untrusted overrides never confer owner authority. The endpoint only dispatches and records execution/lease state; it does no derivation or tagging. At-least-once ticks and ambiguous `:run` outcomes are safe only with idempotent Firestore claims and readback/reconciliation. The dispatcher must revisit due records after failures; a dropped HTTP call cannot strand a saved intent. The parent coordinates ownership of this common dispatch seam; 352 owns its derivation executor and 354 adds Tag-job selection/entry without cloning that executor.

The Tag worker first calls `ClaimProfileJob` against the exact 209 revision, candidate and job ID, checks candidate generation/dictionary/digest and due time, and uses an attempt/lease token so an earlier execution cannot finish a later retry. It loads the previous complete set or durable staging index once, then evaluates only missing keys and keys whose content/input/rule digest changed. Unchanged completed decisions are copied by revision, with no model call. Removed tags and removed items are absent from the new expected product and trigger **zero** model calls. Source and concept decisions stay independent even when they describe the same entity. Provider errors receive a finite policy (for example three attempts with bounded exponential retry); only failed keys are retried. After exhaustion, persist `incomplete`, `missing_count`, and a bounded error code; keep old `active` unchanged. Explicit user retry reuses all completed decisions and schedules only missing keys.

The bounded package takes an injected `Evaluator` and Project-scoped immutable `Store`; no provider implementation or endpoint is wired. The reviewed 334 experiment used requested alias `jev-latest`, and all 23 actual responses reported `jev-1.13.0` ([experiment report](../../../../LWC-334-profile-exec/experiments/lwc334-profile-tagging/REPORT.md)); that is evidence for an explicit accepted returned-ID policy, not a promise about future aliases. The package's `configured_model` and `returned_model` are separate, and a returned ID outside the pinned allowlist is missing work. The parent confirmed Jev direction for the later real adapter; DeepSeek is not a silent substitute. Synthetic fake responses in package tests are clearly labeled and make no model quality claim.

Before calling 209 `ProfileJobTransition(...ready...)`, verify the completed set and rules objects by readback. Pass their exact revisions, zero missing count, and `coverageComplete=true`. 209's existing transaction checks the current revision/candidate/job/generation, manual confirmation (or compile-auto source), and expected active pointer before atomic activation. On CAS conflict, read back: if the exact wanted active tuple already committed, report idempotent success; otherwise mark conflict/incomplete or superseded and retain the old active tuple. No query reader sees a staging row. The existing 209 `ClaimProfileJob` currently treats `running` as idempotent without an execution lease, and its ready transition trusts a caller-supplied coverage boolean; the worker integration must add or prove execution fencing and artifact readback before activation. Do not claim these guarantees already exist.

## Deployment and retained-generation gates

Read-only repository inspection shows `deploy/environments/{development,production}.yaml` defines the existing `olw-pipeline{,-dev}` Job, BFF service account, bucket, Firestore database, and one worker secret. `deploy/components/worker.sh` updates **only the existing worker image**; it does not provision a Profile Tag Job, Scheduler trigger, dispatcher service identity, or IAM. The BFF already invokes Cloud Run Jobs v2 `:run` using a metadata access token and container env overrides in `internal/handler/v1/endpoints.go`; reuse that request/response pattern and URL validation with a separate allowlisted Profile Job URL. The existing pipeline worker entry and publish path are LWC-353 owned and should not be repurposed for Tag work without its coordination.

Required reviewed provisioning, per environment: a Profile Tag Cloud Run Job/image/entry/config with project bucket, Firestore database, bounded provider secret access, timeout/concurrency/retry settings; a shared due-work Cloud Scheduler job targeting the authenticated dispatcher and a dispatcher service account; `roles/run.invoker` or the exact Cloud Run Jobs execution permission for the dispatcher on each Profile Job, `roles/run.invoker` for Scheduler on the dispatcher service, `roles/iam.serviceAccountUser` only if needed by the selected execution API/override; Firestore indexed due-work query plus read/write permissions for dispatcher/worker; scoped GCS read and create-only object permissions; Secret Manager accessor only for the Tag worker identity; API enablement for Scheduler/Run/Firestore/Storage/Secret Manager as applicable. Validate exact IAM bindings and runtime identity through read-only provider readback before any DEV execution. No cloud state, credentials, or deploy configuration was changed for this document.

Generation retention is a separate hard gate: manifests and generation files for every generation still named by an active tuple must remain readable; source snapshots must also remain immutable and readable. The `previous_generation_id` link alone does not provide a by-ID pin API or retention policy. A new G2 compile can update `current.json` while G1 remains active, so G1 Query reads must continue to pin G1, or G2 publication must be gated until G2 Tag coverage and active CAS can move together. Garbage collection may remove a generation only after no active/candidate/job/Query lease references it; deletion and digest mismatch must fail visibly, never silently borrow current bytes. LWC-353 and LWC-355 must agree on this before Query hard filtering ships.

3. Evaluate `match`, `no_match`, `unknown`, `not_applicable`; all four count complete. Inject timeout/malformed provider response; no decision is written, retry only missing key to finite exhaustion, state becomes `incomplete`, and old active tuple remains byte-for-byte unchanged.
