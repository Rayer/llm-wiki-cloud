## Owner disposition recorded

1. Add an explicit `--force` escape from the unresolved-target gate. It is opt-in, never the default or automatic. Its allowed operation and exact bypass must be narrow and written down; it does not grant general runtime, credential, IAM, or Production authority.
2. Preserve deployment source, immutable artifact/provenance, target, and prior/candidate identities. Keep these distinct from the executor SHA and checkpoint-schema compatibility so an engine bug fix can recover a compatible retained checkpoint without whole-engine byte equality.
3. Do not make an unregistered recovery workflow a prerequisite. Use the already registered formal DEV entry and existing Actions authority. Do not require separate workflow registration or a default-branch change, and do not remove component recovery operations.

## Draft contract

### 1. Explicit force escape

The proposed operator interface is an optional boolean `force`, default `false`, carried through the registered DEV dispatch and reusable workflow to the engine's `--force` flag. It applies only to Stage 2 `deploy` of a new ready DEV attempt whose plan ID differs from the unresolved target attempt. A full `release` may forward it only after Stage 1 has produced the new attempt's ready checkpoint; prepare itself is unchanged. The flag bypasses exactly the `target-has-unresolved-attempt` rejection in `Engine.runtime_guard` when the latest target record was read successfully and belongs to the other attempt. It does not skip the latest-checkpoint lookup or make a partial lookup authoritative.

With `force` omitted or false, the existing guard and normal reconciliation behavior are unchanged; an unresolved old attempt still blocks the new deploy.

The force path never resumes or replays the old unknown mutation, edits its checkpoint, or automatically rolls it back. The new attempt keeps its own release/artifact provenance and snapshots actual provider state into its own prior record before mutation. The operator explicitly accepts that the old mutation may already have been accepted or may become visible later, so deploying the new candidate can duplicate or race that mutation. Force itself performs no rollback; if the new attempt later has a known failure, only existing r2 compensation for that new invocation's changed components applies.

Force does not bypass a failed or incomplete latest-state read, `stale-checkpoint`, `target-checkpoint-unavailable`, plan/checkpoint integrity, target or component selection, artifact/receipt applicability, deployment provenance, saved prior identity, or provider deploy/readback verification. It cannot be used for rollback, reactivate, tag, readback, or the old unknown attempt. Automatic compensation never sets force. No interactive confirmation gate is proposed; the explicit new-release deploy and explicit flag are the escape hatch. This draft grants no force path for Production.

When force actually bypasses that gate, the formal result records `force_bypass: "target-has-unresolved-attempt"`; this is outcome metadata, not another gate or state rewrite.

### 2. Release identity and executor compatibility

The release attempt remains bound to its original deployment source SHA, release tag, target and normalized configuration, selected component set and build-input identities, applicable DEV provenance, immutable receipt/artifact identities, and saved prior/candidate identities. In particular, a correction must not rewrite `plan.source`, receipt `build_sha`, artifact digest/handle, `dev_reference`, target configuration, or the provider identities in `state.components[*].prior` and `candidate` merely to run newer engine code. Plan integrity and exact latest-checkpoint sequence checks remain.

Minimum migration proposal: keep legacy `plan.schema: 2` bytes and IDs immutable, verifying their digest with the old rule that includes `engine` and `engine_content`; treat those values as creation-time provenance and do not compare them with the current executor. Decode the current schema-less `state.json` shape (required `plan`, `status`, `components`, `sequence`, optional `builds`) as `checkpoint_schema: 1` after validating those fields and the plan link. New plans use `plan.schema: 3`: `source` remains the deployment source SHA, while `executor_sha` is invocation metadata outside the release identity hash. The release identity hash covers source, branch, target/config, tag, selected components and input identities, and DEV provenance. Artifact build SHA, target configuration, digest/handle, and provider provenance remain independently bound by their existing receipts and applicability checks. New or normally rewritten state writes explicit `checkpoint_schema: 1` and the current `executor_sha`; it preserves the original plan ID and component prior/candidate identities. A read-only operation does not rewrite a legacy checkpoint merely to annotate it.

Read-only `readback` may use a newer executor when it can decode the retained plan/checkpoint and validate the exact target and artifact identities; it performs no provider or checkpoint-state mutation. A mutating operation additionally requires a supported checkpoint schema, a successfully read and integrity-checked latest target record plus retained attempt checkpoint, and the existing operation-specific prior/candidate/provider checks before writing. An unsupported or unreadable checkpoint stops before provider mutation. For Stage 1 resume, compare a legacy plan with a new request by the release-identity fields above; if equal and the existing prepared/ready, runtime-unstarted and build-handle checks pass, continue using the retained legacy plan ID and state rather than importing handles into a newly identified attempt. If release identity differs, only existing compatible completed receipts may be reused; unresolved build handles still stop under the current cross-plan rule. No executor change authorizes build resubmission.

Legacy compatibility preserves the old attempt ID and sequence while decoding. The `plan.schema: 2` digest is checked with its original full-body rule; absent `checkpoint_schema` means the validated legacy state shape above. A matching Stage 1 resume adopts that verified retained plan ID/state in the new job, and a runtime operation mutates only after the existing same-plan/latest-sequence and provider-state checks pass. The reader must not rewrite a retained plan, import unresolved build state across a changed release identity, or treat an unknown checkpoint schema as compatible.

### 3. Recovery through the registered DEV entry

Use `.github/workflows/deploy-dev.yml` as the formal DEV operator entry and route its explicit recovery operations through the existing reusable `.github/workflows/cd.yml`. Keep the existing concurrency group, Actions artifact access, protected Development environment, and current runtime authentication/permission chain. The normal `release` default stays unchanged. No separate recovery workflow registration, default-branch change, or loss of `rollback`, `reactivate`, `deploy`, `tag`, or `readback` is required.

The checkout revision and retained release source are distinct values: `executor_sha` is the registered workflow's current reviewed `github.sha` and selects the code checkout; `plan.source` remains the deployment source SHA. `cd.yml` validates the executor SHA against the checkout and, after downloading the pinned artifact, validates the retained plan ID, source, target, tag, components, receipts, and provenance before invoking the engine. Normal release/promotion supplies the same source for both roles where they coincide. Recovery executes the newer reviewed executor against the unchanged retained plan and artifacts.

The PR87 source contains `.github/workflows/recover-deployment.yml`, but source-file presence alone does not establish that GitHub registers it. Per this disposition, its platform registration is not a prerequisite and must not be changed to unblock DEV recovery. The existing `cd.yml` reusable path and the component-level engine recovery operations remain authoritative.

## Three-point interface for Owner discussion

- **Force:** `force: boolean = false` at the registered DEV workflow, forwarded only to engine `--force` for Stage 2 deploy after a new attempt is ready. The new plan ID differs from the old unresolved attempt and uses the already-required explicit release tag; no tag is generated. It bypasses only `target-has-unresolved-attempt`; when used, `result.json` records `force_bypass: "target-has-unresolved-attempt"`. The old checkpoint/history remains untouched and retained. No confirmation prompt or automatic old-attempt rollback/replay.
- **Legacy compatibility:** `plan.schema: 2` keeps and verifies its original full-body digest; validated schema-less current state maps to checkpoint schema 1; new plan schema 3 hashes release identity without executor identity, and new state carries explicit `checkpoint_schema: 1` plus `executor_sha`. A matching Stage 1 resume keeps the retained plan ID/state; changed release identity cannot import unresolved handles.
- **Workflow identity:** current reviewed `github.sha` is `executor_sha`/checkout ref; `plan.source` remains deployment source and is checked against the downloaded, plan-hash-verified artifact and its receipts. Use the existing registered DEV wrapper and `cd.yml`; do not register a separate recovery workflow.
